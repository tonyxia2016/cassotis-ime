# 言泉输入法 iOS 版第 0 阶段报告

2026-11-07。前提：先自用，不上架。下面的数字全部来自实测，环境逐项标明。真机是 iPhone 15 Pro（iPhone16,1）、iOS 27.2，Release 构建，无 Full Access。

## 结论

**四条通过标准在这台 iPhone 15 Pro 上全部达到，建议继续。** 内存余量很大，延迟是最紧的一条：按真人打字的节奏，单键 P95 在 74–89 ms 之间，离 100 ms 不远。按决定不测老机型，所以结论只对这台手机成立；在更慢的手机上，延迟可能超过 100 ms。

| 标准 | 目标 | 真机键盘扩展实测 | 判定 |
|---|---|---|---|
| 冷启动 | ≤ 30 MB | UIKit 8.9 MB；SwiftUI（fcitx5-ios 面板）15.6 MB，首次提交后 18.4 MB | 通过 |
| 1 万键后 | ≤ 55 MB | SwiftUI 21.7 MB，峰值 25.9 MB；UIKit 21.4 MB，峰值 25.3 MB | 通过 |
| 连续 30 分钟不被杀 | 不被杀 | SwiftUI、开学习和上下文，1,804 秒、8,493 键，未被杀；结束 28.9 MB，峰值 32.8 MB | 通过 |
| 单键 P95 | ≤ 100 ms | 连续打字 53.1 ms；按真人节奏 74.0 ms，开学习和上下文 88.5 ms（P99 118.8 ms） | 通过，余量小 |

冷启动指扩展打开词库之后：引擎在第一次按键时打开，打开本身只增加约 0.1 MB。延迟包含界面更新。“真人节奏”指每键之间停 170 ms，约每秒 5.5 键。

## 1. 键盘扩展真机数字

|---|---|---|---|---|---|---|---|---|

| SwiftUI，连续 | 10,006 | 171 s | 15.6 | 21.7 | 25.9 | 153.9 | 8.9 / 53.1 / 79.2 | `87b8ed8b46c2e479` |

内存单位 MB。两个“连续”运行的候选摘要与 macOS 相同；真人节奏的 1,519 键与 iOS 模拟器相同。

**延迟的主因是 CPU 降频，不是缓存。** 同样的键，按键之间停 170 ms 后，P50 从 8.9 ms 升到 20.2 ms；把缓存放大到 25% 几乎没有改善。降低延迟要从别处入手，比如在按下而不是抬起时开始计算。

**内存上限远高于预期：约 177 MB。** 在这台手机上，`phys_footprint` 加 `os_proc_available_memory()` 稳定约为 177 MB，压到被杀的实测也印证了这一点（第 6 节）。fcitx5-ios 在 iOS 18.7.8 的 iPhone 15 上观察到的约 77 MB 不适用于这台 iOS 27.2 的手机。上限随机型和系统版本变化。

## 2. FPC 工具链：不用换编译器

- Homebrew 的 FPC 3.2.2 直接能交叉构建 iOS 运行库和引擎用到的包单元，没有遇到“3.2.2 无法构建 iOS”的问题。
- 引擎源码未改动时就能编译到 `aarch64-ios`，没有错误。
- 编译器没换，`nc_engine_intf.pas` 里的 3.2.2 ARM64 绕过继续有效，不需要回归。
- `aarch64-iphonesim` 也不需要 main：FPC 通过 clang 汇编，`scripts/sim-clang-wrapper.sh` 把目标改成模拟器即可。
- 候选在 macOS、iOS 模拟器、iPhone App 进程和键盘扩展里逐键相同。

## 3. 引擎静态库

已完成：C ABI（`macos/src/embed/cassotis_core.h`）包住 `DispatchRequest`，复用 macOS 的 `EngineClient`，只换传输层；SQLite 改链接时绑定；路径由宿主注入；只带 `dict_sc.db`，不含神经模型。

需要记住的约束：

- 链接必须加 `-no_fixup_chains`。FPC 的 `FPC_THREADVARTABLES` 有未对齐指针，chained fixups 会报错。
- 神经模型宿主单元在这个构建里没有编译进去，所以 `nc_char_lm_host.pas` 的 `LoadLibrary` 是被整体排除，不是改成静态绑定。静态绑定留到模型阶段。
- iOS 27 SDK 构建的 UIKit App 没有 scene 生命周期会直接崩溃。
- 所有调用要在同一条长寿命线程上。默认用 `cmem`，内存在 macOS 上比 FPC 堆低约 2.5 MB。

## 4. 内存工作

同一语料回放 1 万键，App 进程内或 macOS CLI，单位 MB：

| 环境 | 配置 | 打开后 | 结束 | 峰值 | P50 / P95 / P99 ms |
|---|---|---|---|---|---|
| macOS | 桌面上限 | 15.1 | 67.5 | 71.6 | 5.2 / 37.6 / 61.1 |
| macOS | 收紧后 | 6.5 | 20.8 | 21.0 | 6.1 / 39.7 / 63.3 |
| iPhone App 进程 | 桌面上限 | 20.4 | 50.4 | 54.5 | 5.4 / 39.3 / 63.5 |
| iPhone App 进程 | 收紧后 | 11.2 | 17.2 | 19.9 | 5.7 / 37.9 / 59.5 |

收紧后 = 缓存上限 6%、SQLite 页缓存 2 MB、mmap 320 MB、`dict_base_query_path` 按需读取、不预热单字权重。键盘扩展用的就是这套配置。

**对候选的影响：没有。** 关掉引擎的时间预算后，桌面上限、6%、3% 三档在 3 万键、740 句压力语料上逐键相同。

**引擎有墙钟时间预算，这一点要注意。** 开着预算时，机器繁忙会改变长句结果：上述 740 句里有 3–4 句的过程或提交不同；机器空闲时同配置重复运行完全相同。较慢的手机更容易碰到预算，长句质量可能下降；这台 iPhone 15 Pro 上的文档语料没有碰到。

增长最快的缓存：

- `nc_engine_intf.pas`：`m_lookup_text_units_cache`，每键约 1.3 条。
- `nc_dictionary_sqlite.pas`：`m_prefix_popularity_cache` 和 `m_contains_popularity_cache`，各约每键 2 条，原来没有上限，已加。
- 同样没有上限、已加的：`m_lm_transition_loaded_queries`、两张 session latest-text 表。

**发现一个 macOS 版也有的泄漏。** FPC 3.2.2 的 `TQueue.Dequeue` 只移动低位指针，队列不清空就不回收空间，每次入队漏 8 字节，引擎有 14 处 FIFO 淘汰。修复是 `nc_dequeue`：12 万键不重复压测（macOS，收紧后）结束时，从 73.0 MB 降到 26.2 MB，P95 从 49.4 ms 降到 40.9 ms。这个修复对 macOS 版同样有用，建议单独合回去。

## 5. fcitx5-ios UI 复用：可行

- commit `7f4fecf` 的 `uipanel` 已接到言泉引擎，并在真机键盘扩展里跑完上面的全部测量（`app/KeyboardSwiftUI/`）。
- 接缝很小：8 个 UIPanel 函数、4 个 Fcitx 函数和几个路径 JSON 工具。`FcitxProtocol.keyPressed` 正是 `Fcitx.processKey` 的替换点。
- 剪贴板历史只做了桩，它依赖 GRDB。`KeyboardViewController.swift` 没有直接复用，撤销、光标移动、文档轮询等逻辑以后要移植。
- iOS 26+ 上候选栏会被系统滚动边缘效果模糊，要加 `.scrollEdgeEffectHidden(true, for: .all)`。
- 在真机上，SwiftUI 面板比 UIKit 多占 6.7 MB（冷启动 15.6 vs 8.9 MB）；打满 1 万键后两者几乎一样。

## 6. 闲置、真实上限与权限

- **闲置 10 分钟（SwiftUI）：没有线性增长。** 前 7 分钟一直是 15.4 MB，约 7.5 分钟时跳了一次 1.1 MB，之后稳定在 16.5 MB 直到结束。
- **压到被杀的真实上限：约 177 MB。** 键盘扩展里不断分配并写满内存：8 MB 步长时，最后一次存活是占用 175.3 MB、可用 1.7 MB；2 MB 步长时是 176.0 MB、可用 1.0 MB。再多一步，进程就被系统终止。系统没有写 JetsamEvent 报告，拉系统日志要 root 权限，所以“因内存上限被杀”是根据进程内数字推断的。压测后键盘恢复正常。
- **`increased-memory-limit`：跳过。** 用现有通配 profile 签名后安装失败（`0xe8008015`），需要给显式 App ID 开这项能力。
- **Full Access 没有打开，也不需要。** 真机上无 Full Access 时，键盘扩展能读 App 包里的词库，也能在自己的容器里建立和写入用户词库。Full Access 只能由用户在设置里手动打开，App 无法代开。
- **App Group 无 Full Access 时能否读：未验证。** 需要在团队 TR78TGFZDE 下注册 App ID 和 App Group，用户还没有答复。自用方案不依赖它。
