# 言泉输入法 iOS 版第 1 阶段报告：字符模型走 Core ML

2026-11-07。真机是 iPhone 15 Pro（iPhone16,1）、iOS 27.2，Release 构建，`cmem`，无 Full Access；第 6、7 节是 2026-11-08 另测的 iPhone XS Max 和 iPhone 12 Pro Max。Mac 是 M1 Pro。下面的数字全部来自实测。

## 结论

**macOS 版用的那个字符模型，现在在 iPhone 键盘扩展里照常运行，首选率几乎翻倍，第 0 阶段的四条标准全部满足。** 延迟靠“延后排序”达标：按键先返回只按词库排的候选，键盘空闲时再取回模型排好的候选（第 5 节）。

模型没有缩小，也没有重新训练：同一个 11 层、int8 权重的 `char_lm.onnx` 转成 Core ML 后，在神经网络引擎（ANE）上运行。权重留在 ANE 一侧，不计入扩展进程的内存。第 0 阶段估计“手机端要换一个小得多的模型”，这个前提已经不成立。

| | 不加载模型 | 模型，按键里排序 | 模型，延后排序（默认） | 标准 | 判定 |
|---|---|---|---|---|---|
| 整句首选率（365 句） | 37.3% | 65.7% | **65.7%** | — | — |
| 冷启动（模型就绪后） | 9.0 MB | 12.7 MB | 12.8 MB；SwiftUI 19.1 MB | ≤ 30 MB | 通过 |
| 1 万键后 / 峰值 | 15.6 / 17.7 MB | 32.9 / 40.8 MB | 32.5 / 40.7 MB | ≤ 55 MB | 通过 |
| 单键 P95，连续打字 | 49.1 ms | 86.3 ms | **51.4 ms** | ≤ 100 ms | 通过 |
| 单键 P95，真人节奏 | 74.0 ms（第 0 阶段） | 127.0 ms | **79.1 ms**（P99 104.7） | ≤ 100 ms | 通过 |

“连续打字”是 UIKit 键盘连续回放 1 万键；“真人节奏”是 SwiftUI 面板、每键之间停 170 ms，与第 0 阶段相同。延迟都含界面更新。换成自写界面、打开后台补全之后的数字见第 9 节。

- **质量：** 首选率几乎翻倍，与 macOS 上 ONNX Runtime 版本的 66.6% 相当。
- **延迟：** 模型让每键的工作量变大：在按键里排序时，真人节奏 P95 到 127 ms。改成延后排序后，按键回到不加载模型时的速度。按真人节奏时，1,464 次模型排序有 1,462 次在下一个键之前补上；上屏结果与在按键里排序几乎完全相同（Mac 上 365 句有 364 句一样）。
- **代价是计算量：** 每个键要算两遍候选，一遍按词库，一遍用模型。连续回放 1 万键的总耗时，Mac 和 iPhone 上都多约 38%；耗电没有测。
- **macOS 同样受益：** 同一组语料，Core ML 与 ONNX Runtime 首选率持平，单键 P95 从 113 ms 降到 80 ms，回放进程的内存从 396 MB 降到 160 MB（Mac 上用同一个引擎回放，第 2 节）。macOS 版现在优先用 Core ML，失败时退回 ONNX Runtime。
- **设备要求：** iOS 18 / macOS 15，且神经引擎至少 16 核（A14、M1 及以后）。iPhone 12 Pro Max（A14）实测四条标准全部满足，真人节奏 P95 91 ms，见第 7 节；iPhone XS Max（A12，8 核）跑不了这个模型，见第 6 节。不满足时，键盘自动不用模型，候选与第 0 阶段相同；macOS 则退回 ONNX Runtime。

## 1. 做法

**转换（`macos/scripts/char_lm_coreml.py`）。** 用 coremltools 的 MIL 直接按 ONNX 的结构重建网络，不经过 PyTorch：

- int8 权重和每通道比例原样保留（`constexpr_blockwise_shift_scale`），不做第二次量化。
- 激活改用 float16。ONNX 版的 int8 静态激活范围，在 ANE 上用假量化表达会算错。
- 自定义的 `TrieAttention` 改写成普通的 matmul + 加性掩码 + softmax。ANE 上融合的 `scaled_dot_product_attention` 带加性掩码时结果错误。
- 残差流最大到 700 左右，LayerNorm 在 float16 下会溢出，所以先乘 1/16 再归一化，eps 相应除以 256。
- 每个序列长度一个函数（64、128、256），共用一份权重，形状全部固定，整个网络都能放在 ANE 上。
- 编译后的 `char_lm.mlmodelc` 约 170 MB，元数据记录源 ONNX 的 SHA-256。

**运行时（`macos/src/host/native/nc_char_lm_coreml.mm`）。** 导出与 ONNX Runtime 桥接库完全相同的 `nc_lm_*` 函数，评分、记忆、续写、纠错算法都直接复用 `nc_char_lm_ort.inc`，只替换“跑一次网络”这一步。

- Core ML 的网络没有“之前 token 的 K/V”这一输入。所以 ONNX 版保存 K/V 的地方，这里保存每个 token 的链（从 BOS 到它的 id 和位置）。
- 每次运行把新 token 的链合并成一棵前缀树重算一遍。一个 token 的结果只取决于它的链，因此和用 K/V 算的一样。
- 超过最长函数的树，按整条链拆成几次运行。
- 每个长度的输入缓冲只分配一次；所有长度的输出写进同一块缓冲（`outputBackings`），按最长函数分配，256 × 12017 × 2 字节，约 6 MB。

**接入引擎（`macos/src/host/nc_lm_runtime.pas`）。** 两个模型宿主（字符模型、整句纠错）不再自己加载库，统一调这个单元：

- **核对：** 先核对词表和读音表的哈希；用 Core ML 时，再核对模型记录的源 ONNX 哈希与 `runtime_manifest.json` 是否一致。不必在每次启动时对 170 MB 权重算哈希。
- **iOS：** 链接进来的 Core ML 运行时直接静态绑定。
- **macOS：** 先试 `libcassotis_coreml.dylib`，不行再用 `libcassotis_ort.dylib`。

**嵌入构建的变化：**

- 重新编进了两个模型宿主。
- C ABI 增加 `char_lm`、`char_lm_async` 两个选项和 `cassotis_core_model_state`。
- 模型在后台线程加载，就绪前候选不用模型。

## 2. 结果是否正确

**后端逐项对照（`bench/lm/ab.sh`，Mac）：** 用同一组输入分别调用 ONNX Runtime 和 Core ML 两个库。

| 用例 | 数量 | 平均 \|Δlogp\| | 首选一致 | 真值排第一（ORT / Core ML） | 耗时 P50（ORT / Core ML） |
|---|---|---|---|---|---|
| 单字同音候选 | 322 | 0.064 | 99.7% | 96.0% / 95.7% | 11.0 / 5.0 ms |
| 双字词同音候选 | 292 | 0.095 | 99.7% | 97.3% / 96.9% | 10.0 / 5.0 ms |
| 大前缀树（300–390 个 token，需拆分） | 12 | 0.218（8 字合计） | 100% | 100% / 100% | 97.2 / 16.0 ms |
| 整句纠错（每句 1–2 个同音错字） | 58 | — | 输出 100% 相同 | 纠对 89.7% / 89.7% | 44.5 / 29.3 ms |

- 差异来自激活精度：ONNX 版是 int8，Core ML 版是 float16。
- 关掉记忆（`CASSOTIS_LM_NO_MEMO=1`）时，Core ML 的单字用例和纠错结果与开记忆时完全相同；大前缀树只差 0.004，来自拆分方式不同引起的舍入。这说明链的记账是对的。

**整条输入链路（Mac 回放，615 句语料前 365 句，约 1 万键）：**

| 后端 | 首选率 | P50 / P95 / P99 | 进程内存（结束 / 峰值） |
|---|---|---|---|
| 不加载模型 | 37.3% | 4.9 / 35.5 / 57.3 ms | 80 / 84 MB |
| ONNX Runtime | 66.6% | 15.2 / 113.4 / 151.7 ms | 396 / 493 MB |
| Core ML | 66.0% | 12.6 / 79.9 / 119.0 ms | 160 / 174 MB |

- 用的是桌面缓存策略，关掉引擎时间预算；原始数据在 `results/mac-lm-*.json`。
- 两个后端都开着 Tab 续写和一键重排的后台任务，与 macOS 桌面版一致；第 4 节说明为什么 iOS 默认关掉它们。
- ORT 与 Core ML 有 94.2% 的句子上屏完全相同。其余是近似并列的候选，各有对错：只有 ORT 对的 5 句，只有 Core ML 对的 3 句。

**不加载模型时与第 0 阶段逐键相同：** `char_lm=0` 时，语料前 300 句的摘要仍是 `24ca8ec5e807ec1e`，iOS 配置 1 万键仍是 `87b8ed8b46c2e479`。真机键盘扩展上也一样。

**加载：**

- **冷编译每个扩展一次：** 每次重新安装后，第一次加载模型时，系统为 ANE 编译三个函数，用了 7–14 秒。编译在系统进程里进行，扩展峰值内存只到 18.3 MB。两个键盘扩展读的是同一个模型文件，但各编译一次。
- **之后很快：** 每次扩展进程启动，加载约 0.1–0.2 秒。
- **不阻塞打字：** 加载在后台线程，期间候选不用模型。

**内存：**

- 加载后扩展只多 3.5 MB。
- 打满 1 万键后多 17 MB。主要是每次运行的 float 结果行（新 token 数 × 12017 × 4 字节）、ANE 的输出缓冲和模型宿主的缓存。
- 可用内存最低仍有 144 MB。

## 4. 延迟花在哪里

在 Mac 上用 iOS 内存策略回放 3,015 键，记录每次 Core ML 运行：

- **主线程共运行 4,953 次，平均每键 1.6 次，合计占回放时间的 43%。** 按长度分：64 有 3,427 次，平均 30 个 token，每次 5.2 ms；128 有 1,103 次，每次 7.6 ms；256 有 423 次，每次 20.9 ms。
- **固定成本：** 每次运行约 4 ms 起步（单独测：16 个 token 4.1 ms，64 个 5.2 ms，128 个 6.5 ms，256 个 16.2 ms），主要是每次都要把约 150 MB 权重流过一遍。所以多加短函数几乎没有收益。加一个 192 长度的函数也试过，回放 P95 没有变化（77.6 对 78.0 ms），没有采用。
- **手机上的单次耗时：** 键盘扩展里直接用 Core ML 测，64 长度 4.5 ms，128 长度 4.7 ms，256 长度 12.4 ms（`results/mltest-ne-*.json`）。当时模型还带 512 长度：单次 31.5 ms，用过一次后扩展内存多约 25 MB；引擎的运行不超过 256 个 token，所以去掉了。
- **重算的比例：** 运行的 token 里，调用方真正需要的只占 58%，其余是重算的上下文；按长度补齐后，实际算的位置是需要的 3 倍。
- **按键路径之外的浪费，已去掉：**
  - 引擎每键都会把 Tab 续写和一键重排排进后台线程，结果靠前端轮询取回。iOS 键盘不轮询，这部分（同样回放里后台又跑了 4,449 次）只是在抢 ANE。
  - 嵌入构建里它们现在默认关闭，`char_lm_async=1` 可打开。
  - 关闭后 Mac 上 P95 从 82.0 ms 降到 78.0 ms，结束内存从 108 MB 降到 87 MB，首选率不变。
  - 更新（2026-11-08）：键盘有了补全行，会轮询取回这些结果，于是键盘又把它们打开了（嵌入构建的默认值不变，由键盘设 `char_lm_async=1`）。在手机上的代价见第 9 节。

## 5. 延后排序

引擎在十几处用到模型，散在候选生成的各个阶段，还有两处纠错，没有单独的“重排”一步可以挪走。所以做法是整次算两遍，第一遍让模型暂时“未就绪”。模型还在加载时，引擎本来就这样运行。

**引擎侧（嵌入构建的 `char_lm_deferred` 选项，键盘默认打开）：**

- 按键时，两个模型宿主暂停：所有调用点都当模型未就绪，退回词库排序。按键马上返回，结果带“待定”标志。
- 前端轮询（请求 17）时，如果代号还是这个键的，就恢复模型，用 `rebuild_candidates_for_char_lm` 对当前输入重建一次候选并返回。重建和改配置、删用户词时的重建是同一个 `build_candidates`。
- 新的按键会让旧的轮询作废。用户已经翻页或移动选择时不重建，看到的列表保持不变。

**键盘侧：**

- 引擎线程只在没有别的任务时才轮询，所以连续快打时中间的键不会等模型。
- 轮询进行中来了拼音字母或退格，就调用 `cassotis_core_interrupt`：宿主切回暂停，这次重建跳过剩下的模型调用很快结束，结果丢弃，反正下一个键会重建。
- 空格、回车、选候选不打断轮询，等它跑完，所以上屏的是模型排好的结果。如果按空格时轮询还没开始，上屏的就是当时显示的词库排序。

**结果：**

- **Mac：** iOS 内存策略、每键后轮询，回放 1 万键：首选 241 句，与按键里排序相同；365 句里 364 句上屏一样，剩下 1 句两种方式都没打对。按键 P95 从 83.3 ms 降到 44.9 ms，轮询 P50 / P95 为 10.8 / 72.5 ms。不开延后时，候选摘要与改动前逐键相同。
- **macOS 桌面配置（2026-11-08）：** 桌面缓存策略、Core ML、关掉引擎时间预算，在 Mac 上回放（`results/mac-desk-*.json`）。连续 1 万键：单键 P50 / P95 / P99 从 11.6 / 77.0 / 114.5 ms 降到 5.6 / 38.8 / 63.4 ms；真人节奏 1,519 键：从 30.6 / 112.7 / 158.3 ms 降到 23.4 / 67.8 / 94.6 ms。首选句数不变（241 句、35 句）。
- **macOS 输入法（2026-11-08，`results/mac-socket-*.json`）：** 现在默认打开。macOS 的引擎是独立进程，打断放在服务端：轮询期间一个线程窥探（`MSG_PEEK`）客户端 socket，新到拼音字母或退格就打断重建。前端的轮询改为先发出，在之后的 25 ms 定时器里取回，按键不再等轮询。用 `macos/tools/bench/socket_replay.cpp` 照输入法的方式通过 socket 回放 1,519 键：间隔 170 ms 时，单键 P50 / P95 / P99 从 37.0 / 131.8 / 181.5 ms 降到 16.2 / 86.2 / 156.3 ms；间隔 80 ms 时，从 32.8 / 129.7 / 183.5 ms 降到 15.5 / 69.3 / 113.3 ms。首选都是 35 句。下一个键按下时还没答复的轮询，两种间隔分别有 61 次和 403 次。这里的数比上一条高：上一条用嵌入构建，没有后台任务；这里是真正的 macOS 引擎，Tab 续写和一键重排照常在后台运行，按键里排序时也有 660 个键带待定结果。
- **Tab 补全（2026-11-08 修正）：** Tab 续写和一键重排起初在按键时就排进后台。延后排序下，那时用的是词库排序，等轮询用模型重建后，结果大多对不上而被丢掉。现在改为等轮询重建、整理好显示的一页之后再排，与按键里排序的次序相同。每键等结果稳定再比较（`results/mac-socket-completions-*.tsv`，1,496 键）：补全与按键里排序不同的键从 374 个降到 7 个，带模型续写的键从 149 个回到 520 个（按键里排序 521 个）。后台续写现在真的在用模型，会和下一个键的模型那一遍抢神经网络引擎，上一条的 P95 / P99 因此比修正前（75.8 / 99.9 ms）高。
- **iPhone，连续打字：** 按键 P95 从 86.3 ms 降到 51.4 ms，与不加载模型时的 49.1 ms 相当；轮询 P50 / P95 为 10.9 / 72.1 ms。
- **iPhone，真人节奏：** 按键 P95 从 127.0 ms 降到 79.1 ms，P50 从 45.2 ms 降到 29.8 ms。1,464 次轮询有 1,462 次在下一个键之前完成，只有 2 次被打断。轮询 P50 / P95 为 20.8 / 76.3 ms。

## 6. iPhone XS Max

iPhone XS Max（iPhone11,6）：A12 芯片，8 核神经引擎，4 GB 内存，iOS 18.7.11，Release 构建，无 Full Access。键盘扩展刚打开时占 7.5 MB、可用 69.5 MB，**上限约 77 MB**，不到 iPhone 15 Pro（约 177 MB）的一半。

**模型在 A12 上不能用。** 宿主 App 里直接用 Core ML 测（`results/xs-mltest-*.json`），三种计算方式都不行：

| 计算方式 | 64 长度单次推理 | 加载三个长度后的内存 | 说明 |
|---|---|---|---|
| 神经引擎（默认） | 599 ms（128 长度 1.3 s，256 长度 3.0 s） | 1.7 GB | Core ML 没能把模型放上 A12 的神经引擎，权重解压进进程 |
| 仅 CPU | 215 ms | 11 MB（只测 64 长度） | 权重按内存映射读，省内存但太慢 |
| GPU | 61 ms | 613 MB（只测 64 长度） | 首次推理 4.5 s |

对照：iPhone 15 Pro 神经引擎上，64 长度单次 4.5 ms，加载后只多 0.8 MB。

**保护：** 如果不拦住，键盘扩展在 XS Max 上加载模型时内存会冲到几百 MB，被系统杀掉，而且每次打开键盘都会重来。所以 Core ML 后端打开模型前做两道检查（`nc_char_lm_coreml.mm`）：

- 神经引擎少于 16 核就直接拒绝，不加载任何权重。
- 通过的设备先只加载最短的函数，跑两次推理：加载完成后的一次运行超过 100 ms，或两次运行让内存多出 40 MB 以上，就放弃。加载本身不算，因为首次为神经引擎编译要好几秒。

试过用 `MLComputePlan` 判断算子能否上神经引擎，但不能用来做保护：

- iOS 18.7 上它不支持多函数模型。
- iOS 27 上它能给出结果：15 Pro 的 305 个算子有 297 个在神经引擎上，按估计成本占 79%，其余是词嵌入查表和几个类型转换。但计算过程会让进程内存冲到 177 MB，正是键盘扩展的上限。

**XS Max 键盘扩展实测（模型被拒，`results/xs-*.json`）：**

| 运行 | 冷启动 | 1 万键后 / 峰值 | 可用内存最低 | P50 / P95 / P99 ms（含界面） | 首选率 |

## 8. 遗留与下一步

- **计算量：** 延后排序让每个键多算一遍词库候选。原来设想复用已算过的 token（K/V）来省电、让模型结果补得更快，实测后不做，见第 10 节。
- **按下即算：** 已做（2026-11-08，见 README）。15 Pro 带模型、每键按住 80 ms、间隔 170 ms：字母从抬起到显示 P50 / P95 从 20.1 / 53.4 ms 降到 0.1 / 0.1 ms，上屏结果不变，模型轮询结果 92 次全部采用（`results/dev-tap-spec*.json`）。
- **macOS 的延后排序：** 已做（2026-11-08，第 5 节）。引擎进程加了跨进程打断，输入法默认打开。通过 socket 按真人节奏回放 1,519 键，单键 P95 从 131.8 ms 降到 86.2 ms，首选和 Tab 补全不变。按下即算本身对 macOS 没有用：实体键盘按下时系统就把按键交给输入法，没有手指按住的那段等待。
- **Tab 续写和一键重排：** 已做（2026-11-08，第 9 节）。
- **安装体积：** App 从约 320 MB 增加到约 490 MB，模型占 170 MB。自用不受影响。
- **模型更新：** 换模型后第一次加载会重新为 ANE 编译，15 Pro 约 9 秒，12 Pro Max 约 17 秒，期间候选不用模型。
- **老机型：**
  - XS Max 用不了模型，真人节奏 P95 也超标（112 ms）。“按下即算”可能对它最有用。
  - A13（iPhone 11，8 核神经引擎）同样会被拒绝，但没有实测。
  - A14（12 Pro Max）能运行，四条标准都满足，但余量比 15 Pro 小，见第 7 节。A15/A16（16 核）没测过，神经引擎比 A14 快，应能运行。
  - 12 Pro Max 和 XS Max 的键盘扩展上限都是约 77 MB，15 Pro 约 177 MB。内存余量要按这个上限算，不能按手机的总内存估。

## 10. K/V 复用：实测后不做

第 8 节原来估计，把 K/V 作为模型的输入输出、只算新 token，能把模型那一遍的计算量省一半以上。这个估计数的是 token，而神经引擎上的时间主要不取决于 token 数。在 M1 Pro 上实测后，决定不做。原始数字在 `results/kv-trial.txt`，脚本在 `bench/kv/`。

**时间花在哪里。** 键盘配置（iOS 内存策略、延后排序、后台补全），真人节奏回放 1,519 键，模型共运行 4,604 次，37.7 秒，平均每键 3 次、24.8 ms：

| 来源 | 运行次数 | 时间 |
|---|---|---|
| 引擎线程，给候选打分 | 1,043 | 15.8 秒（42%） |
| 引擎线程，整句纠错（逐步的束搜索） | 1,326 | 8.6 秒（23%） |
| 后台，Tab 续写（一步一个字） | 1,572 | 8.2 秒（22%） |
| 后台，续写打分和一键重排 | 661 | 5.1 秒（14%） |

**一次运行的耗时主要由两部分决定，都和 token 数关系不大：**

- **固定开销：** 连续运行时，16、32、64、128、256 长度分别是 4.03、4.38、4.94、5.94、15.11 ms。
- **冷启动：** 神经引擎一有空闲就降下去。64 长度在两次运行之间空闲 5 ms 就要 8.9 ms，空闲 10 ms 以上约 15 ms，空闲 400 ms 也是 15 ms。打字时键与键之间总有空闲，每段连续运行的第一次都要多花约 10 ms，这次回放里合计约 9.3 秒，占总时间的 25%。阈值这么短，调整时机也避不开。`MLOptimizationHints` 的 `fastPrediction` 没有效果（4.93 对 4.98 ms）。

**K/V 函数能放上神经引擎，但不划算。** 每个函数固定“新 token 数”和“旧 token 槽位数”，所有层的 K/V 合成一个输入 `[1, 22, 槽位, 1024]`，新 token 的 K/V 作为输出（`bench/kv/kv_proto.py`）。数值是对的：和 numpy 版本比，|Δlogp| 平均 0.017、最大 0.047，最可能的字完全一致。用真实形状比较，含拷贝 K/V 的时间：

| 一次运行 | 不带 K/V | 带 K/V | 差别 |
|---|---|---|---|
| 新 1 个 + 旧 15 个 | 4.92 ms（64 长度） | 4.15 ms | 省 16% |
| 新 6 个 + 旧 18 个 | 4.93 ms（64 长度） | 4.17 ms | 省 15% |
| 新 25 个 + 旧 18 个 | 4.99 ms（64 长度） | 4.65 ms | 省 7% |
| 新 75 个 + 旧 13 个 | 5.96 ms（128 长度） | 7.19 ms | 慢 21% |
| 新 110 个 + 旧 16 个 | 6.04 ms（128 长度） | 7.39 ms | 慢 22% |

用 IOSurface 零拷贝传旧 K/V 没有帮助。

**账：** 按连续运行的耗时估算这 4,604 次运行，现在 24.6 秒；加 16、32 长度的普通函数 23.0 秒；再在 K/V 占优的小运行上用 K/V，21.8 秒。K/V 比短函数只多省 1.2 秒，是总时间 37.7 秒的 3%。代价是多一套函数，再加一份 K/V 存储：一个 token 45 KB，记忆里最多留 344 个，约 15 MB，而键盘扩展的内存正是最紧的资源。短函数本身也只省 4%，第一次加载还要多编译几秒，也不加。

运行次数才是大头，但不改算法减不下来：整句纠错和 Tab 续写都要算出这一步才知道下一步算什么。

**留下的改动：只跑要读的行。** `CharLmScore` 里一个 token 的分数是从它父节点那一行读出来的，所以候选文本的最后一个字，只有在要问它后面的字时才需要跑。ONNX Runtime 版还得跑它，为了存 K/V；Core ML 版不存 K/V，以前算了也用不上。现在 `CharLmRun` 多一个参数，说明这次要读哪些行，Core ML 版只跑这些行的链。

- **结果不变：** 所有运行强制用同一长度、关掉时间预算，3,015 键的候选摘要与改前完全相同（`a9a2a07a4f907fd9`）。不强制时摘要会变（Mac 上 1 万键 `ccc0b013f54a0ccd` → `09bb35490c39da6a`，首选率都是 66.03%）：一部分运行换了函数长度，而同一棵树在 128 长度算出的数值和 64、256 长度有细微差别（16.5% 的数值不同，平均差 0.0014，最大 0.03，最可能的字相同）。第 7 节写的摘要是改之前的。
- **效果不大：** 实际算的 token 少 16%（Mac 上）。手机上连续打字省 4–5% 的时间，轮询 P95 快约 5%；真人节奏下差别在噪声之内。Mac 回放的峰值内存少约 10 MB（88.6 → 77.2 MB），手机上没有重现。
